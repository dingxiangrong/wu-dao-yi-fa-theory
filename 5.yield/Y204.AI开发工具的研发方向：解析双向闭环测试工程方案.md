# Y204.AI开发工具的研发方向：解析双向闭环测试工程方案

## 一、双向闭环测试 官方定义

核心思想：同一份需求 → 双向并行 → 最终对账
正向（开发端）：基于需求 → 编写代码 → 产出真实业务数据（后端服务、Provider、文件存储、JSON、上下文池）
逆向（测试端）：基于完全相同的需求 → 直接生成验收基准（模拟调用方、维护预期数据、维护本地基准状态）

闭环判定：对账校验
开发端实际产出数据 == 测试端预设预期数据
对账不相等，直接定位问题点，打回修复；对账相等，本轮闭环通过。

## 二、方案核心价值

1. **约束 AI 代码生成的随意性**
测试端预先建立基准作为标尺，AI 生成的开发实现必须对齐基准，避免 AI 自由发挥带来逻辑漂移。

2. **BUG 直达根因，拒绝表层现象排查**
对账不一致可直接锁定故障位置：
- Provider 存储逻辑异常
- writeSysContext 写入异常
- readSysContext 读取异常
- sysContext.json 字段冗余污染等底层根因，不再停留在业务现象层面。

3. **引入事务一致性思想保障数据完整性**
将数据库事务 “要么全部成功，要么全部不生效” 的思想迁移到文件存储体系。
- 主体对象写入
- 聊天记录分页写入
- 业务上下文独立写入
整套存储动作具备原子性，杜绝部分写入、数据残缺。

4. **多套测试环境完全隔离互不污染**
user_simple、user_chat、user_task、workspace_test 测试实例相互隔离。
多用例并行执行，不会出现测试用例互相篡改数据、交叉污染的问题，满足企业级回归测试要求。

## 三、四套标准闭环用例

1. **简单闭环测试**
测试身份：user_simple
目标：上下文创建、基础数据结构正确性
执行步骤：创建上下文 → 读取上下文 → 执行模拟操作 → 持久化保存 → 双向数据对账比对

2. **聊天闭环测试**
测试身份：user_chat
目标：聊天记录追加、分页存储、ChangeItem 状态同步
执行步骤：创建上下文 → 读取上下文 → 追加聊天消息 → 更新本地基准 → 双向比对

3. **打开简单闭环（会话恢复）**
测试身份：user_chat
目标：进程重启、重连之后上下文数据一致性
执行步骤：加载已有历史会话 → 接续执行业务聊天 → 对账校验恢复前后数据一致

4. **新建任务闭环测试**
测试身份：user_task
目标：任务上下文、业务状态流转、引导态流程正确性
执行步骤：创建会话 → 普通聊天交互 → 新建业务任务 → 执行业务聊天 → 双向对账比对

## 四、当前需要落地的核心工程问题

1. **Provider 具备独立存储逻辑，禁止直接透传对象**
不能上层传入什么对象就原样存储什么对象。Provider 承担数据防腐、业务隔离职责，需要做数据转换、过滤、规整，而不是简单转发。

2. **存储结构拆分，拒绝全部数据混杂在单一 JSON 文件**
- sysContext.json：仅保存系统主体信息
- chatHistory：聊天记录独立分页存储
- currentBizContext：业务上下文独立存储
实现数据分层结构化存储。

3. **读写接口成对对称，支持事务一致性**
writeSysContext /readSysContext
writeTaskContext /readTaskContext
写入与读取必须一一配套，保障读写链路对称，具备局部事务保障能力。

4. **测试体系支持多实例并行**
通过新增独立测试实例实现多场景回归，不修改、不污染旧有用例，构建稳定回归测试集。

## 五、方案总述

|双向闭环测试 = 前端模拟调用方 + 后端实现对账校验 + 数据事务一致性保障 + 测试实例环境完全隔离<br />AI 时代面向模块级的高质量工程质量保障机制。|
|---|
